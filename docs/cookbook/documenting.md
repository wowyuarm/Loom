# 写文档与交接

怎么写能力页、怎么写一次工作的交接。纪律与落点见[维护规则](<../AGENTS.md>)；本文给可直接用的骨架。

## 能力页骨架

一页一个职责，顺序固定，缺哪节说明“无”而不是省略：

```markdown
# <能力：读者会搜索的词>

<一句话：这个能力让什么成为可能。> 整体协作见[架构](<../architecture.md>)。

## 配置与服务
字段、inject、提供的接缝；链接到声明，不抄签名。

## <核心行为>
当前实现的真实行为与时机。每条都能指到源码或测试。

## 失败与限制
接受后失败、并发、崩溃恢复、权限——写验证过的，没验证的写"未验证"。

## 模型看到什么
提示、工具、notice、上下文——Individual 的体验，与工程体验分开。

## 验证入口
对应测试与它们证明/不证明什么。
```

写法：先事实后解释；具体路径、配置落点、命令直接用链接；数字、阈值、顺序不复制——链到实现，让一处改。不复制上游 README 整段，写 Loom 怎么用、差异在哪、去哪核对。

## 交接（handoff / 工作汇报）

写给没有这段对话的人：目标与当前原子动作；已确认的事实（各自验证过还是只是听说）；决定与理由；已产生的仓库外副作用（文件、进程、提交）及其状态；一个明确的下一步。机械细节（命令、路径、行号）放结论后面，完整但不淹没结论。Team 场景的消息与交接规范见工程指令，这里不复制。

## 收口工作记录

`.scratch/` 中的设计或研究落地后：结论按落点进 maintained docs（能力页/架构/指南/adr），工作项按[其规则](<../../.scratch/AGENTS.md>)归档。归档不回写为当前事实；未实现的部分留在记录里，不进能力页。仍有效的跨能力取舍（为什么这样而不那样）写进 [adr](<../adr/README.md>)，只记真实做过的决定，不预写意向。
