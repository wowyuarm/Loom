# Planning Workflow

本文档适用于负责目标澄清、研究、设计收敛和任务拆解的 Agent。它与协作工具无关；讨论面、任务系统和代码托管平台都可以不同。

## 先判断工作类型

- 目标或边界不清：先补事实和问题，不建实现票。
- 需要比较方案并形成稳定合同：写研究结论或 spec。
- 合同完整且存在独立、可验收的垂直切片：再建实施 ticket。
- 已有明确合同的简单修复：直接交给执行 Agent，不为了形式预建 spec/ticket。

## 推荐方法

- `grilling` / `to-questionnaire`：找出缺失事实、真正的产品选择和必须升级的问题。
- `to-spec`：形成 Problem、Solution、范围、非目标、依赖、测试缝和验收条件。
- `to-tickets`：把完整 spec 切成端到端可交付的工作，不按角色或阶段拆票。
- `triage`：判断已有本地问题记录的状态和下一步。
- `wayfinder`：不熟悉仓库入口或文档路径时定位材料。
- `domain-modeling` / `codebase-design`：术语或模块边界需要收敛时使用。

这些方法按需要选择，不是固定流水线。规划 Agent 负责判断是否需要；执行 Agent 不重新发明产品合同。

## 设计记录和事实源

当前行为以代码、测试和真实运行状态为准；稳定合同进入 `CONTEXT.md`、`docs/` 或 ADR；进行中的研究和当时决定可以记录在 `.scratch/<topic>/`。旧 scratch 记录不为后续演化回写，后续稳定结论另写正式文档。完整讨论、评审、部署和验收证据保留在协作面或任务系统中。

同一主题需要再次审查时，新建带日期的 round，并在 summary 中固定证据采集时间、代码基线、状态和结果。不要把新结论回填进旧 decisions，也不要给同一轮的每个 research 文件重复添加时间。

规划结果至少说明：目标、范围、非目标、依赖、完成证据、审查/验收/部署路径、升级条件和未决问题。

## 交接

交给执行 Agent 时提供稳定的 spec 或任务入口、代码范围、禁止扩展的边界和验证要求。任务应能脱离规划对话继续推进；不要要求执行 Agent 读取全部历史记录。
