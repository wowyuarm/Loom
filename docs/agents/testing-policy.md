# 测试策略

测试用于证明一项改动影响的行为，不是每项工作固定跑完的仪式。先选择最窄而充分的证据，只有横切风险、无法可信缩小范围、部署候选或任务合同明确要求时才运行全量。

## 选择证据

- 聚焦测试：运行直接拥有该行为的测试文件，覆盖正常路径、错误路径和边界值。
- 分层测试：`test:fast` 覆盖 Agents、Main Agent、Workspace、Configuration 和轻量解析；`test:runtime` 覆盖 Runtime；`test:host` 覆盖 Channel、CLI、Host、Instance 和 Integration。改动跨层时组合相应层次。
- 组合测试：跨 Runtime、Instance、Host、Channel 或 Workspace 时走真实装配路径，只替换模型、网络、时钟等昂贵或不稳定边界。
- 恢复测试：涉及持久化、取消、重试、并发或进程退出时，分别检查失败前后、重启后权威状态和副作用。
- 可见结果测试：Prompt、tool schema/result、Transcript、CLI 或人的可见行为变化，通过真实组装后的确定性测试检查最终结果；内部字符串断言不能代替入口行为。
- 真实运行验收：模型 Provider、Channel、部署、权限和长期节律只能由真实环境证明，并由任务明确指定的运行或产品角色执行。

## 测试方法

- 优先使用真实实现，只 mock 外部服务或不确定输入。测试自己创建资源并在成功、失败和超时后完成清理。
- 验证外部世界而不是被测对象的自我报告：写入后重读文件，投递后检查 Delivery 或远端事实，恢复后读取权威状态。
- 测试名称陈述行为，不写“正确工作”或实现步骤。回归测试应让对应缺陷真实变红，而不是只命中相邻代码。
- 测试本身可能过时或错误。失败时先对照任务合同、当前代码和真实行为；旧断言与已确认行为冲突时更新或删除测试，不能为让测试变绿而扭曲正确逻辑，也不能无证据地把失败归咎于测试。
- 覆盖率只能说明代码被执行，不能证明组合后的产品可用。不要为了覆盖率保留死分支或添加没有行为意义的断言。

交付时只报告实际运行的检查和结果。未运行的层次保持未验证，不用推断或其他绿色测试代替。
