# 为 agent 建设工作上下文

本文是方针，不是清单：**怎么写 subsystem 文档，以及怎么建设让 agent（人或 AI）在 Loom 高效工作所需的上下文**。随理解更新，不定义代码没实现的行为。

改 `docs/` 前先读 [`README.md`](README.md)（索引与维护纪律）和根 [`AGENTS.md`](../AGENTS.md)（权威顺序）。

## 一、出发点：接缝就是契约

Loom 的设计约束是**插件之间只经 `ctx` 服务与事件交互，不互相 import 实现**。推论：一个插件对外真正稳定、也真正要被别人依赖的，就是它的接缝——提供哪个服务、发什么事件、占哪些系统提示段、用哪些存储域。**接缝就是契约，契约就是最该被写下来的东西。**

agent 在这里高效工作，等于三件事同时成立：

- 接手一个能力时，能读到它的对外契约，**不用从源码逆推**；
- 改完有明确的验证口径，知道**做到什么算完成**；
- 完成的工作项能**闭合归档**，不淤积在 `.scratch/active/`。

这三件事分别对应下面的三、四、五节。

## 二、文档分层：谁定义什么

权威顺序见根 `AGENTS.md`（代码与测试 > `docs/` > DSH 契约 > `.scratch/`）。`docs/` 内部各司其职，不重复：

| 文档 | 回答什么问题 | 什么时候写 |
| --- | --- | --- |
| [`dsh-platform.md`](dsh-platform.md) | DSH 底座怎么组合、Loom 用哪些接缝、怎么跑部署、绑 DSH 的风险 | 已建，随底座认知更新 |
| `subsystems/<cap>.md` | 单个能力的**对外契约**（一个能力一页） | 该能力的接缝稳了、或要交接时（见三、四节） |
| `CONTEXT.md` | 稳定术语与所有权边界（谁拥有哪个域、哪个服务名） | 命名或所有权开始产生歧义时 |
| `adr/NNNN-*.md` | 不可逆的持久化 / 恢复 / session 取舍及其理由 | 做出此类决策时 |

`src/contracts/` 是**类型契约的单一事实源**（纯类型 + ctx 类型增强）。文档不重复类型签名，只引用它：agent 读 `contracts` 拿精确签名，读 subsystem 页拿"为什么、有哪些不变量、和谁协作"。

## 三、怎么写一份 subsystem 文档

**触发信号——不要一次写全，谁稳了写谁。** 满足任一即到写的时机：

- 某能力的对外面（服务名 / 事件 / 工具名 / 存储域）连续几周没再改动；
- 准备把它交给另一个人或 agent 接手。

理由：文档是接缝的缓存。接缝还在动时（例如工具刚改过名），写完即失效，维护成本高于收益。等它稳定再建。

**只写对外契约，不写实现。** 固定骨架，一页足够：

```markdown
# <cap> — 一句话说明这个能力是什么

## 对外契约
- 服务：`ctx.<name>` — 接口见 `src/contracts/<file>`
- 事件：发 `<event>` / 听 `<event>`（各自的语义与触发时机）
- 系统提示段：name / order（静态 section 还是每轮 context）
- 存储域：`loom_<cap>` — 键的布局、是否只增
- 依赖的接缝：inject 了哪些服务、依赖哪些 DSH 行

## 不变量与安全约束
只写代码看不出的：顺序要求、并发假设、失败时的行为、为什么这么设计
```

**不要写进 subsystem 页：** 函数签名（看 `contracts`）、内部数据结构、具体文件路径、实现步骤——这些会过期，且代码是它们的权威。

## 四、解开闭合死锁

`.scratch/AGENTS.md` 的 lifecycle 要求"关闭工作项 → 结论进 maintained docs → 归档"。当 subsystem 文档缺位时，代码已落地的工作项无处安放结论，卡在 `active/`，下一个 agent 只能重读整段历史。规则：

- 代码已落地**且接缝已稳** → 写 subsystem 页 → 工作项归档到 `archive/YYYY-MM/`；
- 代码已落地**但接缝未稳** → 在工作项 `README` 的 status 标注"代码已落地通电，接缝待稳后补 subsystem 文档并归档"。让接手者一眼知道这是已实现、等固化，而非仍在设计。

## 五、更进一步：给 agent 建设工作上下文的思考

以下是方向性建议，按"现在做 / 信号出现再做"分开。避免过度设计——只在真实摩擦出现时建，不预建空结构。

**接缝地图（信号出现再做）。** 单看一页 subsystem 看不到全局；agent 改一处前需要知道"会碰到谁"。`dsh-platform.md` §四已有 Loom 用到的 DSH 接缝表，可在多个自研插件之间的协作变复杂、或出现一次因不了解全局导致的接缝误用后，扩成一张跨插件的"服务 / 事件 / 提示段 order"总表。现在插件少（7 个），源码加那张表已够，先不建。

**CONTEXT.md 术语表（命名产生歧义时做）。** 多插件共享命名空间（`loom_` 域、`ctx` 服务名）。当出现一次命名冲突或所有权误解时，就是建它的时机；`dsh-platform.md` §七的命名约定表是它的雏形。

**完成标准写进入口（可现在做）。** agent 需要明确的"改完跑什么算完成"。当前离线验证三件套：`pnpm typecheck`、`pnpm test`、`dsh --profile loom --dump-config`（组合层，防版本偏斜）。把这条清单放在 agent 接手任务的入口处（AGENTS.md 或工作项 ticket），比留给自觉可靠。

**CI（推 GitHub、开始并行协作后做）。** 单线快速迭代阶段，手动跑上面三件套即可；等主干需要保护、有多方并行改动时，把三件套搬进 `.github/workflows/`，`dump-config` 那条正好自动挡住已知的版本偏斜故障。

**一条贯穿原则。** 文档是 agent 的缓存，缓存要在源头稳定后才建，失效成本才低于收益。这解释了本文所有的"信号出现再做"：不是拖延，是让每一页文档在写下时就已经对得起它的维护成本。
