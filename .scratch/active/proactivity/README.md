- **状态**：after-interaction 已有源码实现并由 `cordis.patch.yml` 装载（第一片，§0–7）。2026-10-12 本讨论已把 Loom 主动性收敛到**活动锚定的 jev-pulse**（[DESIGN.md](DESIGN.md) **§9**）：pulse 优先、锚在"距上次活动多久"的活动时间线上、jev 退二元门控。此前的"下一候选 C / 账的衰老可见"是被移开的支线。**仍未授权新实现或派发**——等 Human 就 §9.7（self-source 给不给）拿个立场后，才把 slice 1 落票。第一片历史设计与验收项见 [issues/01-after-chat-in-place.md](issues/01-after-chat-in-place.md)。
- **最后核验**：2026-10-12（收敛侧，收敛 pulse 形状；下列运行数据与版本事实为 2026-10-09 重核，仍有效）。当前锁定 DSH 为 0.1.7-rc.2、jev 为 0.1.1。DSH `Agent.inbox` 是 Session 持久的 next-turn/next-step 消息队列，与 §8 讨论的逻辑 Inbox 不是同一能力；Schedule 可持久投递 reminder，但依赖 Loom 当前未装载的 Session Controller，且其回执不代表执行完成。
  - **运行数据（journald 近 9 天，推翻本文旧记的「8 次布防 / 3 次 jev / 0 次唤醒」——那是 10-04 的早期快照，已失效）**：布防 119 次，跑到 jev 33 次，判 speak/act 唤醒 5 次（4 speak + 1 act），`check dropped: the generation moved on` 4 次；服务起停行约 25 次（fiber 本地计时器随重启消失，这是布防未响的主因之一）。33 次 jev 的 quiet 概率密集落在 0.44–0.58，另有 0.46/0.47/0.48 三次贴着 0.4 线没过——阈值在真实样本上确实在做事，B 这条线是通的。
  - **材料现状（某部署的 Agent Workspace）**：attention 6 条、全部等人（"等他选/等他叫/等他拍/等他重启/他没定"），**0 条带 horizon**（scaffold 与 orientation 两处都要求带）；attention.md mtime 10-08，threads/index.md mtime 10-01。
  - **关键事实（2026-10-09 实测修正）**：该 workspace **不是 git 仓库**，所以当前机械可得的时间事实只有整文件 mtime。但**整文件覆写并不丢失逐条年龄**——收敛侧 在 /tmp 建仓实测：只改一行、整文件重写，`git blame` 仍精确给出每行最后改动时间。所以"逐条时间无处可存"是错的（我先前的判断），差的只是那个目录没纳入 git。这是可补的前提，不是机制死路。
- **当前前沿（2026-10-12）**：本讨论（2026-10 pulse 收敛，任务 #25）收敛出**活动锚定的 jev-pulse**，已沉淀为 [DESIGN.md](DESIGN.md) §9。要点：活动时间线（interactivity 与 proactivity 同属 activity、共用一条 time-since-activity 时钟）取代"固定钟 + 人输入覆盖"；jev 二元 {quiet, attend}，醒了做什么主体自己定；建造顺序 心跳 → 自写检查 → 外部事件；护栏＝只取 legacy 的活动时间线、不取其认知器官。唯一待 Human 拿立场：§9.7 self-source 给不给。确认后把 slice 1（活动锚定心跳，复用 after-interaction 样板）落成一张票、拟交 实现侧。
  - **（以下为 2026-10-09 及更早的支线状态，保留作历史）** 10-07/10-08 三轮发散（见 materials）已把重心从"C 的一次性时点托付"移走，Human 评价 收敛侧 的 §8.7 C 层形状"很一般"，并定了方向：当务之急是**让 agent 能被 `user` 以外的 kind 唤醒**，然后做**基于 jev 的 pulse**（jev 退到二元 `{quiet, attend}` 门控，醒来后干什么由 agent 自己定），不预建 Inbox 插件、不单独设计 kind 机制（在实现具体功能时自然引入）。§8.7 中仅"到期是状态不是事件""Harness 不对主体看不见的材料行动"两条保留。
  - **收敛侧 的核对结论（2026-10-09）**：`deliver` 硬编码 `source:{kind:'user'}`（`src/agent-runtime/runtime.ts:175`，契约 `src/contracts/index.ts:158` 也只有 `deliver(text)`）属实，这是真卡点，且解法窄、风险低、四处分流点（channels / after-interaction / time-context / context-continuity 的 `ephemeralNoticeSourceKinds`）都已在代码中存在对应接缝。
  - **但"账的衰老可见"这个第一片依赖一个不存在的事实**：workspace 非 git、无逐条历史，机械可得的只有整文件 mtime。而 attention 是**整文件覆写**，改任何一条都会刷新 mtime——"这条 N 天没动"在当前材料形态下派生不出来，只能得到"整个 attention 多久没被碰"。10-08 文档把它当成"零新格式、零解析"的安全第一片，这个前提不成立。
  - **收敛侧 给的推进路线（2026-10-09，2026-10 订阅模式讨论（见该讨论），等 Human 点头）**：三步，顺序是信息顺序而非技术依赖。① **票 03** workspace 纳入 git、harness 每轮机械快照（本身不是主动性，但独立有价值：材料可回退、演化可查；并且它是逐条年龄的唯一来源）。② **票 04** 把逐条年龄 `(14 天未动)` 派生到投影里，纯观测、零手填、不改任何行为——这一步花几乎零成本买到一个能**否决**下游的答案："它拿到时间维度会不会用"。③ 之后才是 kind 解锁 + pulse。理由：先做 pulse 就得接受"衰老可见"这个未验证假设，再用冷却/配额去兜它的空转，而配额正是 Human 自己那条判据所指的理由空洞信号。前两步完全不触碰主体行为，最坏情况只是它无视标记——无自激、无扰民、无外发风险。
  - **已交付并验过、已合并（2026-10-09，2026-10 材料留版与年龄任务，实现侧 执行）**：`main` 已 ff-only 到 `ff93e33`（未 push），合并后门重过（typecheck 0、119/1）。活体 `e1cb200` 单提交 clean 且 blame 通。**等 Human 定重启时机**（服务没重启，功能休眠；回填已决：不做）。后续"它用不用时间维度"观察由 收敛侧 跟。另核：blame 实测冷启动 9.9ms、之后 4–5ms；年龄只在提示词里、不写回磁盘。
