# 未决三条的推演：够旧的线、spill 与 64K 的关系、agent 够得着的入口

日期：2026-10-02。研究侧 写。接 `pre-rollover-context.md` §7 的七条，先啃 ①②④（其余五条见 §5）。

性质：**推演，不是已确认设计**，更不是已实现。数值全部未经真会话验证。源码依据列在每节开头，都只读核过，没动 Loom 源码。

## 0. 先给结论

1. **spill 的 12500 和 64K 不是谁先谁后，是两个不冲突的量纲**：一个管"单条结果不能太肥"，一个管"整窗累积不能太满"。12500 只占 200K 预算的 6%，所以它永远是内圈、到达时就生效；64K 是外圈、到量才动手。**spill 的阈值不用动**，唯一要防的是"两套各按各的算、归因不清"——用一句话把关系钉死即可（§2）。
2. **「够旧」的线不在年龄上，在两件事的交点上**：①主体已转到别的事（那批结果不会再被引用），②缓存反正要重建（改写不白付）。真会话里"旧到什么程度"不是一根固定轮次线，是一个**时机窗口**——旧是必要条件，缓存冷才是动手条件（§3）。
3. **agent 够得着的入口，最省的一档是纯策略**：引擎本就有个不问命令的 `compactIfNeeded('pressure')`，它比硬限用的 `context-overflow` 温和得多（有阈值门槛 + 保近期尾巴）。**用一个更低的水位把它接上、给 agent 发一条"该收了"的提醒，就是够得着的入口**——不用开 `/compact`、不用新造工具（§4）。
4. **但要诚实一点**：靠提醒的入口，agent 手里按的其实还是"读到提醒、然后开口"这个按钮，不是"自己决定什么时候收"。真要给它决定权，得再往前一步（§4.3 说了三档的代价差）。

## 1. 源码依据（本节只是证据，读结论看后面）

三条我逐行核过的事实，后面全靠它们撑：

- **引擎的两个触发口，行为差很多**（`dsh-compaction-basic/lib/index.js:914` 起）：
  - `compactIfNeeded(agent, 'pressure')` —— 先看用量到没到 `thresholdTokens`（默认 `thresholdRatio 0.8`，即窗口的 80%），**不到就直接返回 null 什么都不做**；到了才跑 pruner、才选压缩范围，而且**带近期保留尾巴**（`retainTokens`，默认 `retainRatio 0.16`，即约 16% 的消息预算按原文留在尾部）。
  - `compactIfNeeded(agent, 'context-overflow')` —— **跳过阈值门槛**，先 pruner、再 `selectCompactableRange(..., retainTokens=0)`，**近期保留为零**，硬压到能过为止。
  - `compactNow(...)` 是第三个：**空闲期**手动入口，`selectCompactableRange(..., 0)` 也是零保留；`/compact` 命令调的就是它（`dsh-command-compact`，Loom 已 `disabled`）。
- **Loom 现在只接了最狠的那个**（`src/context-continuity/pressure.ts:66`）：`reduce: (reason, signal) => engine.compactIfNeeded(agent, reason, signal)`，而 pressure 策略硬限那一档传的 reason 恒为 `'context-overflow'`。加上 `presets/loom.patch.yml:83` 的 `auto: false`（关掉引擎自己的 `agent/pre-step` 自动检查）和 `command-compact` 被关——**结论没变：agent 中间没有任何档，只有忍着 / 被硬限按头压一次 / 自己换代。**
- **pressure 策略的决策序是三段**（`@wowyuarm/dsh-context-continuity/lib/pressure.js` 的 `onPreStep`）：低于 handoff 水位 → 什么都不做；到 handoff 水位（Loom 里是 200K 上限那档）→ **一代发一次**提醒（durable latch，重启不重发、换代重新武装）；到硬限 → 强制压一次，**证明不了真的变小就 fail closed**。

新发现的一条，决定 §4：**`reduce` 这个 capability 只是把 reason 字符串原样透传给引擎**（`pressure.ts:66` 没有校验、没有白名单）。也就是说"用 `'pressure'` 而不是 `'context-overflow'` 去触发"这件事，**代码上是一行的事，纯策略层，碰不到压缩引擎本身**。

## 2. ② spill 12500 与 64K/128K：谁是外圈、怎么换算

**先换算。** spill 的 `maxInlineTokens: 12500` 是**单条结果**的内联上限（约 50K 字符）；64K/128K 是**整个窗口**的累计水位。拿 Loom 的真实预算看（`src/context-continuity/retrieval.ts:27-45`：硬限上限 256K、handoff 上限 200K、输出预留 16K）：

- 单条 spill 上限 12500 ≈ handoff 水位 200K 的 **6%**。
- 也就是说：**即使把结果喂到爆，一条也吃不掉 6% 的窗口**；反过来，窗口能涨到 64K/128K，靠的绝不可能是"几条巨无霸结果"（那些早被 spill 按住了），只能是**一堆中等长度的结果 + 交流本身**堆出来的。

**所以答案是：spill 是内圈，64K/128K 是外圈，不是竞争，是两层各管一段。**

- spill 在**结果到达时**（`tools/post-execute`）对**单条**动手，无条件、不分新旧，防"一条东西撑爆预算"。
- 64K/128K 在**每个模型请求前**对**累计**动手，管"堆太多"。
- 触发顺序天然成立：**到达时先压小 → 请求前量到的已是压小后的量 → 外圈触发更晚**。这一点 `dsh-context-plugins.md` §入口核对 也写了，两处一致。

**三条由此推出的结论**：

1. **spill 阈值不用调。** 12500 在 200K 的窗里是安全的内圈值，动它既不能帮外圈减负（外圈的对手是中等结果群，不是巨无霸），反而多一个要归因的变量。**保持不动。**（改成"随窗口水位动态"理论可行，但引入的复杂度没有对应收益——spill 是防塌方的，不是调节奏的。）
2. **重叠部分收益递减，这是好事。** 一条已经被 spill 压成头尾的结果，到了 64K 再裁它，省不了几个 token——所以外圈挑条时**天然应该跳过已有 spill notice 的那些**，它们已经是"最小可回取"形态了，再裁只有噪声没有收益。
3. **真正要钉的是归因**：调试时"窗口为什么在涨"必须一句话能答——先看有没有单条异常（spill 管得住就不会），没有就是累积（外圈的事）。两套阈值用"单条 / 累计"这一个词区分开，就不出现"两套各按各的算"。

**外圈和 spill 之间唯一需要决定的参数**（未决，留给实现）：64K 挑条规则里，**已 spill 的条目要不要直接排除**。我倾向排除（见上条 2），但这要在真会话里看它们到底还占多少——spill 后仍可能有 25%（头+尾+notice），不是零。

## 3. ①「够旧」的线画在哪

**先把"旧"拆成两件事，因为它们经常被混成一根轮次线，而那根线一定画错：**

### 3.1 旧 = 不会被再引用（内容维度）

一条结果"旧到该收"，判据不是它经历了几轮，而是**主体已经转到别的事上、那批结果不会再被引用**。这条我上一版就倾向，现在更确定，理由是机制上的：**模型下一步只能用当前请求里的东西**——只要那批结果还在窗口里且主体还在这件事上，它就随时可能被指代、被纠正、被要求"回到刚才那段"；一转话题，它的价值就掉到"要精确细节时才回去查"，而那件事本来就该走检索（`context_search` / `context_read` / 日志），不该靠常驻窗口。

- 所以**"旧"的真正含义是"已经安全外置了"**，不是"时间过了"。这也是为什么 §1 里"撤走的必须留路"是硬约束——判它不再被引用，前提是真要细节时**查得回来**（Loom 底下是唯一一份 Session log，天然满足）。
- **轮次是这件事的劣质代理**：一个 turn 内可能跑几百轮工具往返（长 loop），也可能一轮就是一次闲聊。按轮数切，前者把还在用的切掉、后者把真正旧的留下。**结论：不按轮次画线，按"话题是否已转移"画。**

### 3.2 但是"够旧"本身不给动手时机（缓存维度）

这里是我这轮想清楚的**关键点**，上一版没拆开：

- **旧，只是把"可以收"打开了；真正让"值得收"成立的，是这次改写不白付。**
- 改写已经发出去过的字节要**重付 prompt cache**（从最早被改处起、后面全部重新计价）。所以：
  - 主体连续干活、缓存还热 → 这时去收，省的 token 抵不过重建缓存的钱，**纯亏，旧也不该动**；
  - 缓存本来就过期了（静置超过 TTL）、或反正要压缩/换代重写 → 这时**顺手多收一点，边际成本近乎零**，旧的就该一次收够。

**所以「够旧的线」不是一个点，是一个交点：**

```
够旧（话题已转 + 已安全外置）  AND  动手便宜（缓存冷 / 反正要重建）
            ↓
        才是"该收"的时刻
```

- **旧是必要条件**：不旧（还在用）→ 无论多便宜都不收。
- **缓存冷是动手条件**：再旧，缓存热 → 这次不收，等下一个窗口。

这一条同时回答了"近了白收、远了没用"的两难：**白收的根源不是线画太近，是画在了缓存热的时候**；**没用的根源不是线画太远，是画在了话题还没转的时刻**。两个失败模式各有一个旋钮，不该拿一根轮次线同时对付它们。

### 3.3 由此，最小起步的挑条规则（可落地、未验证）

机器挑条不需要模型逐条判断（太贵也容易错），用两条硬规则就够第一版：

| 规则 | 取什么 | 为什么这样取 |
| --- | --- | --- |
| **够旧** | 早于"上一次话题转移"的工具结果，且长度 > X 字符 | 话题转移在真会话里可先用粗信号近似（连续的 `message` 调用 / turn 边界 / 主体自己写的材料更新）；精确判定留给真会话调 |
| **动手便宜** | 只在缓存冷窗口里触发（静置 > TTL，或与一次必然的重写同批） | 这是省钱的开关，不是省钱的幅度 |
| **近期保护** | 最近 N 条 / 最近一段按原文留（引擎 `retainTokens` 现成的 16% 尾巴可复用） | 防"模型还没读到刚返回的结果就被裁"，现成 pruner 没这条，得自己补 |

**未决（要拿真会话试，不能推理定）**：话题转移的粗信号具体取什么、X 多大、TTL 取哪家 provider 的值、近期保护给多大预算。**这四条是部署参数，不是设计**，放宿主配置，不写死进引擎。

## 4. ④ agent 够不够得着一个缩减入口

### 4.1 现状复述（一句话）

`auto:false`（引擎自检关）+ `command-compact` 关（`/compact` 没了）+ 无对应工具 ⇒ **agent 手里只有"忍着 / 自己调 `context_rollover` 换代"两极**，中间够不着任何动作。

### 4.2 但入口比想象的近：引擎那档温和的现成没接

§1 的证据说明，**"温和的一档"不是要新写，是引擎里躺着没接**：

- `compactIfNeeded(agent, 'pressure')` 就是**不问命令**的入口（pressure 策略到硬限时调的是同一个函数、只是 reason 不同）。
- 它自带 80% 门槛（不到不压）和 16% 近期尾巴（压了也保尾），**正好是"日常该有的那档"形状**。
- 而 `pressure.ts:66` 的 `reduce` 原样透传 reason ⇒ **在更低的水位加一档，改的是 pressure 策略/宿主那一层，不碰压缩引擎。**

**最小做法（纯策略）**：

> 在 handoff 水位**之下**再设一个水位（比如窗口 65% 或 80%，具体待定）。到那里，给 agent 发一条**一代一次**的提醒（复用 pressure 已有的 durable latch 机制，形状就是现成的 `contextPressureNoticeText`，只是话术换成"可以收一批旧结果了"），并让这档触发的 reduce 走 `'pressure'` reason（温和、带保留尾巴），**不是** `'context-overflow'`（狠、零保留）。

- 不开 `/compact`（那是给人的，且 Loom 明确关了）。
- 不造新工具（`compactionFor()` 这个 port 本来就开着，只是 reason 写死成最狠的那个）。
- 用的是 continuity **已有的** notice + latch + `reductionProven`（收完要证明真变小，Loom 已有），完全在它"当什么时候的裁判、不当怎么缩的工人"的边界内（见 `pre-rollover-context.md` §8）。

### 4.3 诚实的部分：这样拿到的是哪一种"够得着"

三档，代价递增，我先给排序：

| 档 | agent 手里的按钮 | 能不能自己决定何时收 | 代价 |
| --- | --- | --- | --- |
| **A. 更低水位提醒（推荐起步）** | 读到提醒 → 开口（像现在回 rollover 提醒那样） | 否——**触发仍由机器**（水位到就发），agent 只是**被告知后可否决/推迟** | 纯策略，不碰源码机制、不加工具 |
| B. agent 可调的显式动作 | 一个工具（如 `context_reduce`） | 是——自己挑时机 | 新造模型界面，违反"先看现成口"；且要设计它收什么、怎么防滥用 |
| C. 打开 `/compact` | 人类命令 | 是 | 面向人的通道给 agent 用，语义错位；Loom 已有意关掉 |

**我的判断：先做 A。** 理由不是 A 最好，是 A **把缺的那半先补上而零新造**——现在连"被告知该收了"都没有（提醒只在 200K handoff 水位发一次，那是逼换代的信号，不是"可以收一收"的信号）。A 落地后能立刻回答一个悬着的问题：**agent 拿到提醒到底会不会用、用得对不对**。会用 → 再考虑给它 B 那个真正的按钮（那时才谈得上"自己决定"）；不用 → 说明该改的是水位/话术，不是缺工具，B 就不必做。

**一句话**：A 是"够得着"的最小实现（复用现成 port + 现成 latch），但它给的是**建议式**，不是**决定权**；决定权要 B，B 要等 A 的真会话数据说话。

### 4.4 附带清掉的一个隐患

若做了 A，**三个水位必须从同一份预算推**（Loom 已经是：`contextBudgetFrom()` 统一算 usage/handoffAt/hardLimit，pressure 和 retrieval 共用）——新加的那档**也走 `contextBudgetFrom`**，绝不能在别处再算一遍，否则就是 `engineering-review.md` 警告过的"两套阈值各按各的算、归因不清"，正好和 §2 结论 3 是同一个病。
