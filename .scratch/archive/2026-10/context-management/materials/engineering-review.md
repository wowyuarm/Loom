# Loom context 管理：工程判断与证据

研究日期：2026-09-28。本文是候选方向，不是已确认的设计或当前行为说明。

## 判断

现有的持久材料、完整日志、检索和自主 rollover 足够作为底座。实际缺口是：中等体量的历史没有日常缩减入口，只要主体不主动换代，就可能一直拖到压力通知线。

建议沿现有接缝验证**有预算的滚动历史：较早历史的短摘要 + 一段近期内容**。身份、记忆、threads、attention 继续按现有机制现读，rollover 继续留给主体主动选择。先不增加相关性裁判，也不把整套 context 重建列为主动性的前置大工程。

当前候选按 2026-09-28 后续讨论调整为两档：**64K 开始机械裁剪工具内容；达到 128K，先裁工具，仍达到 128K 才做一次旧前缀的模型摘要。** 这替代早先“64K 裁剪后仍超水位就摘要”的建议。数值按当前窗口用量判断，不按累计生成量排程，也不是已证明的最佳阈值。

主要取舍是允许窗口长期处于 80K、100K，以较大的日常输入换较少的摘要调用与历史重写。64K 是开始修剪的水位，不是日常窗口目标。摘要后应明显低于 128K，给继续交流留出空间。

## 从实际需要推导保留方式

模型下一步只能利用当前请求中的信息。无限历史不能全部常驻，而摘要和 handoff 都会丢信息。工程上能控制的是哪些来源进入请求、保留多少原文、何时缩减、如何回查；不能保证模型“自然接住一切”。

| 内容 | 放进窗口的理由 | 合适的处理 |
| --- | --- | --- |
| 当前输入、时间、执行与投递状态 | 决定现在发生了什么、某个动作是否真的做成 | 从现有权威状态注入；不让摘要猜发送是否成功 |
| 主体维护的身份、理解、关切 | 跨话题的判断基础与再次进入旧事的入口 | 继续现读持久材料；自动摘要不替主体更新它们 |
| 近期交流与活动 | 支撑指代、修正、语气和正在展开的思路 | 在有限预算内保留原文；不能只保留任务结论 |
| 更早的经历与大段过程 | 提供背景，偶尔需要精确细节 | 短摘要承接线索，完整日志供检索与展开 |

这里的“近期”必须有工程定义。现成 DSH 后端保留的是按 token 计价的连续尾部，不是“最近几小时的聊天”，也不是完整的几轮人际交流。长工具过程可能把此前聊天挤出这个尾部。第一轮原型接受这条明确的限制，重点验证它是否真的损伤 Loom 的接续；若它成为稳定失败模式，再考虑单独保护有预算的来往记录，不能先声称现成后端已经做到。

原文可查仅保证有恢复路径，不保证主体会意识到遗漏，更不保证搜到正确部分。因此“回查率低”不能单独证明质量好：完全没意识到自己忘了，也会得到低回查率。

## 已核验的 Loom / DSH 行为

1. **持久材料已经持续刷新。** [resident-context 投影](../../../../../src/resident-context/projection.ts#L43)每次装配现读文件。DSH 每步装配，动态快照变化或被压缩遮盖时才再次加入；相同快照不重复加入。持续增长的主要对象是历史，增加一次“重新读身份和记忆”本身不会把历史变短。
2. **200K 是通知上限。** [预算计算](../../../../../src/context-continuity/retrieval.ts#L24)同时受模型窗口与输出预留限制；达到 handoff 水位只发通知，主体仍需调用 rollover。到硬限才强制缩减。普通 [rollover](../../../../../src/agent-runtime/runtime.ts#L239)不带旧前缀，只将 handoff 和待处理输入送入新代；检查点返回另有精确前缀语义。
3. **压缩没有完全禁用。** [preset](../../../../../presets/loom.patch.yml#L59)的 `auto: false` 把压力策略集中给 Loom runtime，硬限仍通过 [pressure host](../../../../../src/context-continuity/pressure.ts#L59)调用后端。新增较早水位应接进同一套策略，不能直接再打开一套互相独立的自动压力处理。
4. **默认摘要是编码任务交接。** 已安装的 `dsh-compaction-basic`（其 `summarize()` 实现）明确要求英文编码助手清单。该后端有公开的 `summarize()` 覆盖接口，可由 Loom 插件提供合适的摘要行为，继续复用计价、替换、配对校验与日志机制；不需要修改安装目录。
5. **两个入口的保留行为不同。** `dsh-compaction-basic` 的 pressure 路径使用近期保留预算；`compactNow` 与 overflow 使用零保留预算，仍留下最后一个节点，并按工具配对向前扩展。不能把 `compactNow` 当成按配置保留近期历史的日常入口。
6. **工具记录包含真正的对话。** [channels](../../../../../src/channels/index.ts#L20)只有 `message` 工具向人发送内容；普通 assistant 文本没人看到。摘要必须分清收到的话、实际发出的话、内部思考、发送尝试及结果，不能按 role 粗分“对话”与“可丢的工具噪音”。当前 conversation focus 是通道和路由，也不是语义上的话题标识。
7. **近期保留还有修剪边界。** pressure 后端先运行工具结果修剪，再选择摘要范围。现成的 `dsh-compaction-tool-result-pruner` 扫描所有超长工具返回，没有近期豁免。因此直接使用它只能得到“保留近期对话与调用记录，超长工具返回仍可能只剩头尾”，不能宣称整个近期片段逐字不变。它不裁剪工具调用里的 `message.text`。当前候选中的近期保护和按工具名豁免需要另行补入，不是现有能力。

### 机械探针：只证明入口行为

在 Loom 安装的包上使用内存 Session、TokenMeter 和返回固定短摘要的 `BasicCompactionEngine` 子类。四轮纯文本 user/assistant 历史，原计价 5044 tokens；`retainTokens=1261`，相当于最后一组问答。全程无模型调用，没有真实关系对话，也没有工具结果修剪器参与。

| 调用 | 处理后估算 tokens | 仍在当前窗口里的原文 |
| --- | ---: | --- |
| `compactNow` | 768 | 只有最后一条 assistant 回答 |
| pressure | 1378 | 最后一条 user 输入及 assistant 回答 |
| 故意返回超大摘要 | 5044 | 拒绝替换，八条原始消息都在 |

断言全部通过，三种情况下原始日志事件均可访问。这些数值来自固定合成摘要，不是实际压缩率，更不是连续性评测。

## 三条可实现路线

| 路线 | 实际改变 | 主要代价与判断 |
| --- | --- | --- |
| 仅把 handoff 通知提前到约 64K | 更早提醒主体决定换代；真正换代后旧前缀不带入 | 改动小，但不能保证通知后就缩减；频繁换代更多依赖主体 handoff，近期原文没有自动保留。适合主动清场，不宜承担全部日常缩减 |
| 较早就地压缩，保留近期尾部 | 仍在当前代运行，把较旧前缀换为摘要，尾部留在上下文 | 推荐先验证。需要 Loom 摘要实现、近期预算和统一触发入口；会产生摘要成本、等待与重复摘要损失 |
| 每轮重新选择历史并配套记忆检索 | 显式重建进入模型的历史片段集合 | 可做，但要新增选择、引用、预算及召回策略。现有证据不足以支持为第一版重做这一层 |

第二条的当前候选在已有的模型请求前检查处执行，待换代状态仍优先处理。每次模型请求前检查体量；一个 turn 内可能有多次模型与工具往返，只在 turn 开头检查会漏掉长 loop 内的增长。检查本身不调用模型。

| 当前窗口用量 | 常规处理 |
| --- | --- |
| 小于 64K | 不处理 |
| 64K 至不足 128K | 只做机械工具裁剪，豁免 `message` 的调用及投递结果 |
| 达到 128K | 先裁一次工具，重新计价；仍达到 128K，才对较早前缀做一次模型摘要，保留近期尾部 |

Human 提出的两档阈值与 `message` 豁免是本轮讨论依据。下面是 收敛侧 建议的实现边界，尚未成为确认的实现合同：

- 第一版机械裁剪先限定为缩短工具返回正文，保留调用信息和配对关系。现成裁剪器不处理调用参数，也没有工具名豁免；若要求连旧调用本身一起移出，就需要额外的成对改写，并保留同一条 assistant 消息里的其他内容。
- 常规裁剪应保护近期一小段工具往返，至少避免模型还没读到刚返回的结果就被裁剪。现成裁剪器没有这条规则；具体保护范围仍需落实，最终不能绕开硬限。
- `message` 的豁免针对工具裁剪。较早的真实交流仍可进入 128K 触发的摘要；摘要保留近期原文的尾部仍按预算划分，不承诺所有真实对话永远原文常驻。
- 同一次常规检查至多做一次模型摘要。DSH 后端默认 `compactionRetries: 1` 可在一次入口中再次摘要，因此不能把默认行为直接当成此候选。失败或不可缩减时交回原有压力处理，仍遵守硬限；摘要上限、近期预算和下一次允许尝试的条件要避免连续空转。

预算必须覆盖真实请求：系统说明、工具定义、现有材料、摘要、保留历史和新输入都占空间。摘要上限与近期预算要给后续输入留余量。128K 是摘要检查水位，不是严格上界：一条大输入、工具配对边界、材料再注入都可能使它越线。配置方式和目标值需要先量实际请求开销，再与模型窗口一起确定；较小模型不能沿用高于安全容量的门槛。

检查、裁剪与摘要都在 loop 的模型请求边界进行。如果 128K 缩减正常生效，现有最高 200K 的 handoff 通知会很少触达，rollover 主要成为主体主动选择。超大单步增长或无法缩减时才可能进入原有压力路径。主体在 loop 内调用 rollover 工具，实际换代在该 turn 结束后执行。

基线不靠空闲五分钟判断“可以遗忘”，也不靠 memory 文件刚写过判断“已经完整沉淀”。这些只能说明经过了时间或发生了写入。体量触发能覆盖持续自主活动，不需要在空闲时反复扫描相同内容。

## 在具体场景里会发生什么

| 场景 | 现状 | 推荐方向的预期行为与限制 |
| --- | --- | --- |
| 上午累积 150K，下午继续日常交流 | 若实际压力水位高于 150K，且主体未主动 rollover，旧历史继续随请求携带 | 上午达到 64K 后开始工具裁剪；到 128K 时先裁，裁后仍超水位才摘要。从现有 150K 接入也按此顺序。若裁剪已降到 100K，可以整个下午不摘要；若执行了摘要，则携带摘要、尾部及新交流。不能事先承诺降到某个 token 数 |
| 晚上再提上午没谈完的事 | 原文若仍在窗口可直接使用；换代后取决于 handoff、材料和回查 | 尾部内有原文可直接接；超出尾部则依赖摘要线索或主体材料。被摘要漏掉且未主动记录的细节，可能不会自然想起 |
| 连续进行大量自主工具活动 | 历史持续增长，最终压力通知或强制缩减 | 体量触发不依赖“任务完成”；尾部仍可能被工具过程占据，旧聊天不享有单独保护 |
| 长时间空闲，回来只聊一句 | 可能重新付较大输入成本，缓存状态取决于 provider | 历史此前已被限制则后续输入较小；若恰在新消息前需要摘要，也可能增加这一次等待和费用。不能承诺这条消息就省钱 |

省钱需要按整段运行计算：摘要请求、缓存重建、后续 cached/uncached 输入和额外检索都计入。没有统一的“空闲 5 分钟，所有模型缓存都失效”的规则。只比较窗口长度不足以证明成本改善。

## Memoh 提供的参照

源码固定在 `felinics/Memoh` 的 `eb735bd01170774f1a99c3a33d6bcafeaec53e9d`，本次只读码，未运行。

- [每 turn 的装配](https://github.com/felinics/Memoh/blob/eb735bd01170774f1a99c3a33d6bcafeaec53e9d/internal/agent/application/service.go#L537)会从事件管线或持久历史准备输入，加入摘要及检索记忆。这些步骤实际决定内容；“重拼请求”这个动作本身不省 tokens。
- [运行内重新选择](https://github.com/felinics/Memoh/blob/eb735bd01170774f1a99c3a33d6bcafeaec53e9d/internal/contextview/provider_step_reselection.go#L27)保护初始输入前缀，只选择新追加的部分，按预算、来源与规则处理。它不是每步语义重判全部历史。
- [工具交换选择](https://github.com/felinics/Memoh/blob/eb735bd01170774f1a99c3a33d6bcafeaec53e9d/internal/contextview/selector_tool_exchange.go#L14)会剥离部分已完成的旧工具交换。Loom 的实际对外发言在工具调用中，不能直接照搬。

可借鉴的是明确的预算、近期保护与较早压缩；这些不要求先复制它的整个 context 子系统。此前“Memoh 每步全量重拼，和 Loom 只差频率”的概括不成立。

## handoff 简化

按 Human 最新要求，主体自己决定 handoff 写什么。工具说明仅需解释：何时发生换代、普通换代与检查点返回分别携带什么、持久文件和外部效果不随之回滚、参数的真实约束。

需要一起处理的未来提示有三处：[orientation](../../../../../src/orientation/index.ts#L44)的 `only work in flight`、`dsh-context-continuity` 的 continuity 工具描述及参数说明里的任务清单、其压力通知里的目标/动作/证据要求。只改其中一个会留下相同引导。

现有工具工厂可覆盖部分词句，但固定句式仍在；完整去除清单应走正式定制接口。已经持久化的历史 handoff 包络不因未来提示优化而重写。当前参数校验仍要求非空 handoff；简化内容引导不自动等于移除这个校验。

## 下一步验证应回答什么

1. **机械行为**：真实装配下区分 64K 工具裁剪和 128K 条件摘要，裁剪后降到 128K 以下不调用摘要模型，同一次常规检查不反复摘要；近期保护和 `message` 豁免生效，工具调用与结果配对正确；新输入、发送结果和原始日志可追踪；失败和单条超长输入遵守硬限。
2. **接续质量**：用同一段“长工具过程后聊天”“隔几小时再提未完话题”“纠正旧说法”“发送结果不确定”的经历，对照现状、提前 rollover、滚动历史。检查具体信息与表达是否错置，而不只问回答是否流畅。
3. **重复损失**：连续压缩多次，检查旧修正、未决事项和原话归属会不会被逐轮改写。短期一次压缩通过不等于长期可用。
4. **完整成本**：计入摘要、缓存、后续请求、回查以及用户等待。是否少读历史只是一个中间量。

这些质量与成本对照尚未执行。本轮完成的是源码核验、无模型机械探针和工程路线判断，未改变 Loom 运行机制。
