# 02 — C 托付的前瞻条目：字段草案

**What this decides:** 一条"明确托付"要长成什么样，Harness 才能读它、到点唤醒它、并在事后与它对账。本票把 [../DESIGN.md](../DESIGN.md) §8.6 列的五个未决（什么算明确托付、期限怎么记、谁能取消/过期/改期、目标渠道怎么定、到期做什么）字段化，并接上 §8.7 的候选形状。

**Status:** draft — 等 Human 拍最后四件事（见文末）。

**依据（已定，不再翻）：** 10-03 三问表态＝前瞻条目才唤醒 / 第一片只收一次性时点或条件 / 到期只交回主体不自动执行；§8.6 已锁"含糊关切不自动成为承诺"；并发纪律继承 after-interaction（真人消息压过检查、交付前复核、fail-closed）。

## 字段表

| 字段 | 必填 | 取值 | 谁能改 | 说明 |
|---|---|---|---|---|
| `id` | 是 | 主体写入时生成的稳定唯一串 | 写入后不可变 | 承诺、取消、过期、完成都拿它对账 |
| `source` | 是 | `self` / `human:<渠道>` / `derived:<id>` | 不可改 | 承诺从哪来。`derived` 表示由另一条目或对话派生，能追回原条 |
| `action` | 是 | 一句明确动作，动词开头 | 主体可改，改了必须重算触发条件 | 没有动作就不是托付（§8.6 已锁） |
| `trigger.type` | 是 | `at`（一次性时点）／`when`（条件） | — | 第一片不收 `every`（周期），对应三问第二问 |
| `trigger.at` | `at` 必填 | ISO 8601 带时区 | 改期＝写新值 + 旧值留痕 | 检查精度待定（§8.7） |
| `trigger.when` | `when` 必填 | Harness 能校验的条件表达 | 同上 | 校验不了＝条件不成立，不唤醒 |
| `target` | 是 | 目标渠道/会话，取现有渠道枚举 | 主体可改 | 到期的 Input 投到哪；不填＝投回产生它的会话 |
| `due_policy` | 是 | `return_only`（默认）／`notify`（预留） | 只有 Human 能升级 | 到期只交回主体重新判断；`notify` 是否留口子待拍 |
| `cancel_by` | 是 | `human` / `owner` / `both`，默认 `both` | 只有 Human 能收紧 | 谁有权取消 |
| `expires_at` | 否 | ISO 8601 带时区 | 主体可设，Human 可提前 | 超过即自动过期；缺省时的默认上限待拍 |
| `status` | 系统 | `active` / `fired` / `expired` / `cancelled` | 只有 Harness 改 | 主体不能自己标完成 |
| `completion` | 后置 | 主体交回的证据说明 | 主体写 | 只在 `fired` 之后有意义，见下节 |

改期、取消、过期都必须留痕：新值生效，旧值不删。否则同一条目对不上账（§8.6 的原话要求）。

## 三种"完成"分开表述（§8.6 要求）

- `enqueued`：到期产生了 Inbox Input。只说明事项进了队。
- `delivered`：Input 送达 `target`。只说明主体看见了。
- `completed`：主体交回结果并附证据。才算完成。

三者不得互相顶替。schedule 插件的投递回执只到 `enqueued`（§8.6 已指出），实现和文案都不能拿它当完成。

## 解析与降级

- 只有满足字段表全部必填项的条目能唤醒 Harness。普通 attention 仍是自由材料，不产生唤醒，也不被从任意文字猜成调度指令（§8.7）。
- 解析失败或字段缺失：降级为普通 attention 材料。不丢弃、不唤醒，下轮由主体自己修复。
- 同一条目不重复唤醒：`fired` 之后必须由主体显式改期才回到 `active`。防止无理由的重复任务（§8.5 末）。
- 到期产生 Input 后，条目本身不消失，留在 attention 里作为对账依据。

## 要 Human 拍的四件事

1. **什么措辞算"明确托付"给 `source=human:<渠道>`。** 我的建议判据：你显式说了动作 + 未来时点或条件（"下周三提醒我……""等 X 出来就……"）。要不要再收紧成"必须你本人原话"，还是助理转述也认？
2. **`expires_at` 缺省时给不给默认上限。** 不给＝永不过期，条目会一直躺在 attention；给（比如 30 天）＝到期自动 `expired`，需要长期承诺就得显式写更远。
3. **`due_policy` 的 `notify` 留不留口子。** 默认 `return_only` 你已点头。`notify` 指到期时顺带给你发一条；留口子意味着到期可以产生对外动作的前置信号，但仍然不替你执行。
4. **改期/取消的历史存哪。** attention 只放当前值 + 最近一次变更，完整历史另放一处（scratch 或 memory）；还是整条历史都塞 attention？前者省 attention 空间，后者单文件可查。

## Acceptance criteria（草案通过后才写实现票）

- [ ] 字段表与 §8.6 五个未决一一对应，无遗留口头约定。
- [ ] 三态 `enqueued / delivered / completed` 在数据结构与对外文案里都有独立表达。
- [ ] 解析失败降级为普通材料有测试覆盖（缺字段、时区缺失、条件无法校验三种）。
- [ ] `fired` 后不重挂，改期必须显式写入且留痕。
- [ ] 普通 attention 的任意文字不会被解析为可唤醒条目（负例测试）。
